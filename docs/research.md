## 1. Phase 1 — TetrisGYM (NES)

Source: <https://github.com/kirjavascript/TetrisGYM> (273 ★, Assembly, active — last push
2026-06-17). README, CHANGELOG and repository tree read in full.

### 1.1 What it is

TetrisGYM is a **practice mod for NES Tetris**, distributed as a **BPS patch** applied by the user
to their own legally obtained USA ROM. The project publishes the patch, never the ROM.

```
File SHA-1: 77747840541BFC62A28A5957692A98C550BD6B2B   (patched output)
ROM  SHA-1: FD9079CB5E8479EB06D93C2AE5175BFCE871746A   (clean input)
```

### 1.2 Lineage

> "This project descends from ejona's [TAUS](https://github.com/ejona86/taus) disassembly and
> [CelestialAmber's](https://github.com/CelestialAmber/TetrisNESDisasm) subsequent take on it."

So TetrisGYM is **exactly the model this project hypothesised**: disassembly → reverse engineer →
modify → add Lab features. The hypothesis is validated by precedent.

### 1.3 How the modification is structured

The source tree is *not* "original code plus a patch file". The disassembly **is** the source, and
Lab functionality is factored into dedicated directories that the original code calls into:

```
src/
  main.asm  reset.asm  boot.asm  header.asm  ram.asm       <- original game, reorganised
  gamemode/          gamemodestate/      playstate/         <- original state machine, split per state
  nmi/                                                      <- render path, split per screen
  modes/             <- ALL LAB FEATURES LIVE HERE
    crash.asm  crunch.asm  debug.asm  drought.asm  events.asm
    floor.asm  garbage.asm  hz.asm  pace.asm  parity.asm
    preset.asm  qtap.asm  saveslots.asm  tapqty.asm  tspins.asm
  presets/  highscores/  keyboard/  nametables/  chr/  data/  util/
```

Key structural decisions worth copying:

* **`src/modes/` is a hard boundary.** One file per trainer. The original game code contains only
  small hooks that dispatch into `modes/`.
* **Nametables (screen layouts) are generated by JavaScript** (`src/nametables/*.js`) and RLE-
  compressed into asm. New UI is authored as data, not hand-written asm.
* **Graphics are PNGs** converted to CHR at build time (`tools/png2chr/`).
* **The whole build runs on `node` alone.** `ca65`/`ld65` are vendored as **WebAssembly**
  (`tools/assemble/ca65.wasm`) so contributors need no system toolchain. `build.js` falls back to
  native `cc65` if present.
* **Mapper is a build flag.** `node build.js -m0|-m1|-m3|-m4|-m5` builds NROM / MMC1 / CNROM / MMC3 /
  MMC5, defaulting to autodetected MMC1-or-CNROM. Retail NES Tetris is **already MMC1**
  (NES-SEROM, iNES mapper 1, 32 KB PRG), so TetrisGYM's default build stays on the original mapper
  and fits inside the original PRG size; the higher mappers buy extra capability, not room.
  Useful precedent that a classic-Tetris community accepts mapper changes — but **not** a precedent
  that expansion is required. See §4.2 for why our situation is different.
* **Feature flags are `-D` defines** (`SAVE_HIGHSCORES=0`, `KEYBOARD=1`, `AUTO_WIN=1`, …).
* **Tests are an emulator-driven Rust crate** (`tests/`, 27 test modules) that loads the built ROM,
  reads the linker symbol file, runs frames headlessly and asserts on memory. Notably
  `cycle_count.rs`, `labels.rs`, `patch.rs`, `rng.rs`, `playfield.rs`, `score.rs`.
* **Free-space accounting is part of every build**: `build.js` prints `N PRG bytes free` parsed from
  the linker map. On a space-constrained target this is essential discipline.

the author built the most-wanted things first.

**The generalisable insight:** almost every trainer is one of four things —

1. **Set up a specific starting state** (floor, setups, transition, B-type, block tool, savestates)
2. **Bias or fix the piece sequence** (drought, seed)
3. **Change one game constant** (DAS delay, marathon speed, linecap, crunch, killscreen)
4. **Show information the original hides** (Hz, input display, pace, score digits)

Categories 1–3 are cheap: they are edits to state the game already keeps. Category 4 is the
expensive one, because it costs VBlank time and screen space. This mapping drives our
prioritisation in `docs/community-research.md`.

## 2. Phase 2 — Game Boy Tetris and its disassemblies

### 2.1 ROM versions

| Version | Common names | MD5 | SHA-1 | CRC32 |
| --- | --- | --- | --- | --- |
| **v1.0** | Tetris (Japan); Tetris (World) v1.0; Tetris (JUE) (V1.0) | `084f1e457749cdec86183189bd88ce69` | `3c1e0dd006f8bba1e4c9594526c7fa7250ca376d`¹ | `63F9407D`² |
| **v1.1** | **Tetris (World) (Rev A)**; Tetris (JUE) (V1.1) | `982ed5d2b12a0377eb14bcdc4123744e` | `74591cc9501af93873f9a5d3eb12da12c0723bbc` | `46DF91AD`² |

¹ Not independently cross-checked; MD5 is the value used by every repo below. ² From
`meithecatte/gbtetris` README; not verified locally.

Both are **32 768 bytes, cartridge type `$00` (ROM ONLY), no MBC, no cartridge RAM** — verified
locally by parsing the built ROM header.

**Version differences** (source: [TCRF](https://tcrf.net/Tetris_(Game_Boy)) via search summary, and
[Hard Drop wiki](https://harddrop.com/wiki/Tetris_(Game_Boy))):

* v1.0 is effectively a **Japanese prototype run (~10 000 cartridges)**. Music is "Minuet", not
  "Korobeniki".
* **Level progression differs.** v1.0: 10 lines per level from 0→8, then **20 lines** per level from
  9→20, independent of start level. v1.1: `startLevel × 10 + 10` lines for the first level-up, then
  10 lines each. Starting on level 9, that is **20 lines in v1.0 vs 100 lines in v1.1**.
* v1.0 does not ignore inputs during line clears, so DAS can be charged through them.
* v1.0 rocket thresholds are 50 000 points lower.
* Net effect: **v1.0 is significantly easier to score on.** It is not the game people play.

> **[VERIFIED LOCALLY]** The per-level gravity table is at **`$1B06` in v1.1** and **`$1B61` in
> v1.0**. Bytes at `$1B06` in the v1.1 build: `34 30 2C 28 24 20 1B 15 10 0A 09 08 07 06 05 05 04
> 04 03 03 02` — i.e. `frames − 1` for levels 0–20, matching the published table
> `[53,49,45,41,37,33,28,22,17,11,10,9,8,7,6,6,5,5,4,4,3]` exactly. The wiki's stated address
> `$1B06` therefore documents **v1.1**, which is further evidence v1.1 is the community reference.

**Recommendation: target v1.1 (Tetris (World) Rev A).** It is the version bundled with ~30 million
Game Boys worldwide, the version the reference documentation describes, the version with the
sane level curve, and the version targeted by the two best disassemblies.

> **CONFIRMED by the community, 2026-08-20** (`docs/community-research.md` §3.5.6). *"Most gb tetris
> carts are version 1.1"* (M-J); *"it should patch with the 1.1 (Rev A / Rev 1)"* (Tolstoj). Note
> also Tolstoj's *"We always use V1.1 but many ROM hackers start with V1.0"* — a players/hackers
> mismatch our v1.1-first choice avoids.

**`kaspermeerts/tetris` — best prose documentation.** Fully self-contained, byte-exact, and its

excellent **secondary reference** for naming and understanding.

**`davFaithid/tetris-disassembly`** — builds v1.0 byte-exact and needs no baserom, but: targets the
wrong version, has essentially **no comments** (1 comment in a 13 501-line file) and 801

and carries an explicit "Commercial usage is expressly prohibited" disclaimer with no licence.
Unsuitable as a foundation.

**`meithecatte/gbtetris`** — the *nicest human-facing structure* of the v1.0 group (per-subsystem
files, a beautifully labelled `wram.asm`/`hram.asm`, prose docs `sprite-system.md` and

modified. Also has no licence. It is however the **best source of memory-map names** and was used
heavily for §3 below.

**`alexsteb/tetris_disassembly`** — MIT and readable (346 comments in 9 038 lines), but its build
output matched **neither** known ROM. Diffed against the verified v1.0 image, 29 983 / 32 768 bytes
(91.5 %) differ across 1 654 runs — far more than any legitimate v1.0↔v1.1 delta. The README's own
to-do list says "annotate data sections (**and solve discrepancies**)", so the "compiles 1:1"
claim in the README should be read as aspirational. Not usable as a foundation.

### 2.3 Toolchain findings

* **RGBDS is the universal toolchain** for Game Boy disassembly (`rgbasm`/`rgblink`/`rgbfix`/
  `rgbgfx`). Official prebuilt Linux x86-64 tarballs exist for **v0.5.2, v0.6.1, v0.7.0, v0.8.0,
  v0.9.x, v1.0.x**; earlier versions are source-only on Linux.
* **RGBDS 1.0 breaks all of these repos.** The pre-1.0 `NAME EQU value` form was removed in favour
  of `DEF NAME EQU value`. Error counts against v1.0.3: `davFaithid` 267, `meithecatte` 597,
  `vinheim3`/`kaspermeerts` untested but certainly non-zero. Migration is mechanical but is real
  work, and must be done *while holding the byte-exact build as the test*.
* Pre-0.5 syntax that also had to be migrated: `name: MACRO` → `MACRO name`; `NAME SET x` →
  `DEF NAME = x`; a user-defined `assert` macro now collides with the built-in `ASSERT`.
* **Recommendation: pin one RGBDS version, vendor the tarball hash, and treat "upgrade RGBDS" as a
  deliberate, separately-reviewed change gated on the byte-exact build still passing.**
  Start on **v0.6.1**, which is what `vinheim3` targets and what built correctly here.

## 3. Phase 3 — Original game architecture

Derived by reading `vinheim3/tetris-gb-disasm` (v1.1) and `meithecatte/gbtetris` (v1.0, whose
memory-map names are clearer). Addresses are v1.1 unless noted.

### 3.1 The three facts that shape everything

1. **The playfield is the VRAM background tilemap.** There is no separate board array. The stack
   lives in BG map A at `$9800`, with a **shadow copy in WRAM** (`wTileMap`, `$C800`, 1 KB). An
   empty cell is the space character tile. Collision is a tile read from the WRAM shadow:
   ```asm
   CheckCollision::
       ld hl, wOAMBuffer_CurrentPiece
       ...
       call SpriteCoordToTilemapAddr
       ld a, h
       add HIGH(wTileMap - vBGMapA)   ; retarget VRAM addr into the WRAM shadow
       ld h, a
       ld a, [hl]
       cp " "                          ; " " == empty
       jr nz, .found_collision
   ```
2. **The active piece is four hardware sprites, not board cells.** It lives in
   `wOAMBuffer_CurrentPiece` as 4 × (Y, X, tile, flags). Rotation changes sprite tile IDs and
   offsets. "Locking" is `HandleLockdownTransferToTilemap`, which writes those four sprites into
   both the VRAM map and the WRAM shadow.
3. **Everything else is a jump table on one byte.** `hGameState` (`$FFE1`) indexes a 54-entry
   `dw` table via the `rst $28` "jumptable" helper.

Consequence for us: *board manipulation* features (garbage, floor, presets, savestates, crunch) are
**tilemap edits**, and must respect VBlank timing for the VRAM half. *Piece* features are OAM edits.
Both are cheap. This is a friendly architecture to hook.

### 3.2 Main loop

`code/inGameFlow.s`, `mainloop.asm` in meithecatte's naming:

```
Init  -> clear WRAM/VRAM/OAM/HRAM, copy OAM-DMA routine to HRAM, ClearTilemapA,
         reset audio, hGameState = STATE_LOAD_COPYRIGHT, enable VBlank+Serial IRQ
MainLoop:
    call ReadJoypad
    call HandleGameState        ; <- jumptable on hGameState
    call JumpUpdateAudio
    if (A+B+Select+Start held) -> SoftReset      ; instant restart already exists!
    decrement hDelayCounter, hFastDropDelayCounter
    wait for hVBlankOccured
    jp MainLoop
```

**`A+B+Select+Start` is already a soft reset.** "Instant restart" — a MUST-HAVE in every training
tool — is therefore *already present in the original game* and needs only to be re-pointed at
"restart this trainer" instead of "boot".

### 3.3 Game states (`hGameState`, `$FFE1`)

Named entries from meithecatte's `constants.asm`:
`0 GAMEPLAY`, `1 GAME_OVER`, `6 LOAD_TITLESCREEN`, `7 TITLESCREEN`, `8 LOAD_MODE_SELECT`,
`10 LOAD_PLAYFIELD`, `14 MODE_SELECT`, `15 MUSIC_SELECT`, `16 LOAD_TYPE_A_MENU`, `17 TYPE_A_MENU`,
`18 LOAD_TYPE_B_MENU`, `19 TYPE_B_LEVEL_SELECT`, `20 TYPE_B_HIGH_SELECT`,
`21 HIGHSCORE_ENTER_NAME`, `36 LOAD_COPYRIGHT`, `37 COPYRIGHT`, `42 LOAD_MULTIPLAYER_MUSIC_SELECT`,
`53 MORE_COPYRIGHT` (v1.1 only). Many slots (2–5, 9, 11–13, 22–35, 38–52) are unnamed or unused.

**Unused jump-table slots are the natural home for new Lab screens.** No new dispatch mechanism is
needed.

### 3.4 Memory map — where Lab state can live

**HRAM `$FF80–$FFFC`** is essentially full (2 bytes free). Key variables:

| Addr | Name (vinheim3 / meithecatte) | Meaning |
| --- | --- | --- |
| `$FF80/81` | `hButtonsHeld` / `hButtonsPressed` | Input |
| `$FF98` | `hPieceFallingState` / `hLockdownStage` | Lock state machine |
| `$FF99` | `hNumFramesUntilCurrPieceMovesDown` / `hGravityCounter` | Gravity countdown |
| `$FF9A` | `hNumFramesUntilPiecesMoveDown` / `hFallingSpeed` | **Gravity reload value ← the speed knob** |
| `$FF9E` | `hNumLinesCompletedBCD` | Line counter (BCD) |
| `$FFA9` | `hATypeLinesThresholdToPassForNextLevel` / `hLevel` | **Level-up threshold ← the transition knob** |
| `$FFAA` | `hStickyButtonCounter` / `hAutoFireCountdown` | **DAS counter** |
| `$FFAE` | `hHiddenLoadedPiece` / `hNextNextPiece` | Piece after next |
| `$FFB0` | `hRandomnessPtrLo` | Index into the 256-byte randomness table |
| `$FFC0` | `hGameType` | A-type / B-type |
| `$FFC2/C3/C4` | `hATypeLevel` / `hBTypeLevel` / `hBTypeHigh` | Menu selections |
| `$FFC5` | `hIs2Player` / `hMultiplayer` | **Selects the deterministic piece source** |
| `$FFE1` | `hGameState` | State machine index |
| `$FFE9` | `hRecordDemo` | **Demo/input recording enable** |
| `$FFEB/EC` | `hDemoPtrHi/Lo` | Demo playback/record pointer |

**WRAM `$C000–$DFFF` (8 KB) has ~4.5 KB genuinely unused.** From the byte-exact
`meithecatte` link map, which declares real per-purpose sections:

| Used | Range | Size |
| --- | --- | --- |
| OAM buffer + score + B-type scoring | `$C000–$C0CE` | 207 B |
| Sprite list | `$C200–$C21F` | 32 B |
| **Randomness table** | `$C300–$C3FF` | 256 B |
| Tilemap shadow | `$C800–$CBFF` | 1 KB |
| Stack | `$CF00–$CFFF` | 256 B |
| High scores | `$D000–$D761` | 1 890 B |
| Audio | `$DF00–$DFFF` | 256 B |

Free: **`$C0CF–$C1FF` (305 B)**, **`$C220–$C2FF` (224 B)**, **`$C400–$C7FF` (1 024 B)**,
**`$CC00–$CEFF` (768 B)**, **`$D762–$DEFF` (2 206 B)**. Total ≈ **4 527 bytes**.
For reference, a full 10×18 playfield snapshot is **180 bytes**. Savestates are comfortably
affordable.

*(Note: `vinheim3` declares WRAM as one monolithic `$C000–$DFFC` section with `ds` padding, so its
link map reports no free space. The gaps above are real; they are simply not expressed as separate
sections. Re-splitting `include/wram.s` into named sections is a small, safe, high-value early task.)*

### 3.5 The randomizer — the single most important subsystem for a Lab

**Single player uses the hardware divider register `rDIV` (`$FF04`), not a seeded PRNG.**

```asm
.random:
    ld h, 3
.try_again:
    ld a, [rDIV]        ; free-running 16 384 Hz counter
    ld b, a
.back_to_zero:
    xor a
.division_loop:
    dec b
    jr z, .try_next_next_piece
    inc a / inc a / inc a / inc a      ; a += 4
    cp SPRITE_TYPE_A                    ; wrap at 7 pieces × 4
    jr z, .back_to_zero
    jr .division_loop
```

The candidate is then filtered by a **bitwise-OR rejection test** against the locking piece and the
preview piece, retried up to 3 times, and accepted unconditionally on the third try. The intent was
to reduce triples of the same piece; the actual effect is a **biased distribution**
([Hard Drop wiki](https://harddrop.com/wiki/Tetris_(Game_Boy)); Henk Rogers takes responsibility):

```
L 10.7 %   |   J, I, Z 13.7 %   |   O, S, T 16.1 %
```

**But there is a second, fully deterministic path already in the ROM.** When `hDemoNumber != 0`
(attract demo) **or `hMultiplayer != 0` (link-cable versus)**, pieces are read sequentially from
`wRandomness` — a 256-byte table at `$C300`, indexed by `hRandomnessPtrLo` (`$FFB0`), wrapping at
256:

```asm
.predefined:
    ld h, HIGH(wRandomness)
    ld a, [hRandomnessPtrLo]
    ld l, a
    ld e, [hl]          ; <- the piece
    inc hl
    ...
```

This is why **both players in a link match get the same pieces** (confirmed by
[TetrisWiki](https://tetris.wiki/Tetris_(Game_Boy)): "Both players have the same piece sequence").

**Implication — this is the project's biggest single opportunity.** A seeded / scripted / drought-
biased / fixed piece sequence needs **no new generator and no hook in the spawn routine**. It only
requires (a) forcing the `.predefined` branch and (b) filling 256 bytes of WRAM. Seed control,
drought, "same pieces for VS", and fully scripted training sequences all collapse into *one*
mechanism that the original game already ships and already tests every time someone plays a
2-player match. This is a materially better position than TetrisGYM had on NES.

*Caveat to verify:* the table is 256 entries and wraps, so sequences longer than 256 pieces repeat.
The attract demo also uses this table, so it must be refilled when entering/leaving a trainer.

### 3.6 Confirmed quirks and dormant features (from `kaspermeerts` README + code)

* **Only 16 of 18 rows are checked for line clears** — the top two rows can never clear. Deliberate,
  per kaspermeerts.
* **Multi-line clears duplicate the top row**, once fewer than the number of lines cleared. Likely a
  genuine bug. Reproducible only at extreme stack heights.
* **`RecordDemo` is called every frame during normal gameplay** but is inert unless `$FFE9`
  contains `$FF`. The write-target addresses are in ROM, so they would need redirecting.
  → **Input recording is half-built into the original game.** A replay feature is far cheaper than
  it would be from scratch.
* **The game writes `1` to `$2000` during `Init`** — the MBC1 ROM-bank-select register — on a cart
  that has no MBC. Both `kaspermeerts` and `meithecatte` flag it. **This means converting the cart
  to MBC1 is close to free: the write already selects bank 1, which is the correct default.**
* **A quarter of WRAM is dedicated to high scores that cannot persist** (no cartridge RAM).
  Adding MBC1+RAM+BATTERY makes persistence nearly free.
* **The game never executes `halt`.** Irrelevant to correctness; relevant if we ever care about
  battery life or add idle work.
* Stereo panning data exists in every song but does not function.
* Several unused routines and duplicated code exist (e.g. `LookupTile` at `$153`, shared with
  Super Mario Land — probably a shared internal library).

### 3.7 Level selection, heart levels, and the practice loop

**[VERIFIED LOCALLY — read from the disassembly]**

Gravity is derived from the level by one short routine (`Call_000_1b43` in meithecatte's naming):

```asm
    ld   a, [hLevel]            ; $FFA9
    ld   e, a
    ld   a, [hStartAtLevel10]   ; $FFF4 - the "heart" flag
    and  a
    jr   z, .no_heart
    ld   a, $0a                 ; heart levels are simply level + 10 ...
    add  e
    cp   $15
    jr   c, .ok
    ld   a, $14                 ; ... clamped to 20
.ok:
    ld   e, a
.no_heart:
    ld   hl, GravityTable       ; $1B06 in v1.1, $1B61 in v1.0
    ld   d, $00
    add  hl, de
    ld   a, [hl]
    ld   [hGravityCounter], a
    ld   [hFallingSpeed], a
    ret
```

Consequences, each of which is a training-tool requirement:

1. **Only levels 0–9 are selectable** from the A-Type menu.
2. **The heart flag is armed at the *title screen*** by holding `Down` while pressing `Start`
   (`titlescreen.asm`, `.start_singleplayer`) — **two screens before the level menu**, undocumented,
   with no feedback until a `♥` renders next to the level. Forgetting it costs a full reset.
3. **Effective level 20 is unreachable from the menu.** `min(level + 10, 20)` with a menu maximum of
   9 yields 19; the clamp is dead code on the menu path. The only routes to level-20 gravity are
   ~100 lines of a heart game or ~200 lines of a normal one.
4. **In a heart game, gravity saturates at in-game level 10.** Levels 10–20 of a heart run are all
   level-20 speed. Any speed-progression trainer must account for this.
5. **Boot costs ~4.2 s of unskippable copyright screen in v1.1.** `HandleCopyrightScreen` checks
   only `hDelayCounter` and has no input test (250 frames @ 59.727 Hz). The *second* copyright
   screen, v1.1-only, *is* skippable (`MoreCopyrightScreenDelay` tests `hKeysPressed`). v1.0 has one
   125-frame screen (~2.1 s).

Adding menu navigation (title → game type → music → level), **returning to a chosen practice speed
costs roughly 15 seconds and an undocumented button combination — and half the speed range cannot be
chosen at all.** This is the strongest single argument for Milestone 1 (direct level select 0–20 with
a heart toggle, plus instant restart): it is not a convenience feature, it is the difference between
one attempt and twenty.

### 3.8 Rendering and VBlank budget

The VBlank handler is **already close to full**:

```
VBlankInterrupt: serial send -> VBlank_HandleLineClearBlink
                 -> ShiftRow19 ... ShiftRow2   (18 unrolled calls)
                 -> VBlank_TypeBScoringScreen -> hOAMDMA
                 -> VBlank_HighscoreTilemap -> conditional RenderScore (x2 maps)
                 -> reset rSCX/rSCY, set hVBlankOccured
```

DMG VBlank is ~4 560 dot-cycles (~1.09 ms, ~1 140 CPU cycles at 1 MHz M-cycles). Any new HUD
rendering competes with this. **New per-frame rendering is the scarcest resource in the project** —
scarcer than ROM (which we can expand) or WRAM (which has 4.5 KB free). Design Lab HUDs to write
few tiles per frame, or to write only on change.

## 4. Phase 4 — Hardware constraints

| Constraint | Value | Impact on this project |
| --- | --- | --- |
| CPU | Sharp SM83, 4.194304 MHz (1.048576 M-cycles/s) | Ample. The original game is idle most of the frame (it never `halt`s). |
| Frame rate | 59.727 Hz | All timings are frame counts; matches the published tables. |
| VRAM | 8 KB, `$8000–$9FFF` | Two BG maps (`$9800`, `$9C00`) both in use. Tile budget is tight; new UI should reuse existing font tiles. |
| WRAM | 8 KB, `$C000–$DFFF` | **≈4.5 KB free.** Not a constraint. |
| HRAM | 127 B | **Full — 2 bytes free.** New fast-access variables must go in WRAM or displace something. |
| **ROM** | **32 KB, ROM ONLY, no MBC** | **The binding constraint. See below.** |
| Cartridge RAM | **None** (`$149 = $00`) | No savestate/highscore persistence without changing the cartridge type. |
| Screen | 160×144, 20×18 tiles, 4 shades | Playfield is 10×18 of those 20 columns; the right ~7 columns are the HUD. Little room for new HUD. |
| Sprites | 40 OAM entries, **10 per scanline**, 8×8 or 8×16 | The active piece uses 4. Plenty spare, but the 10-per-line limit matters for any wide sprite-based overlay. |
| Input | 8 buttons, no analog | `A+B+Select+Start` is taken (soft reset). Menu input design must work around this. |
| VBlank | ~1.09 ms | **Scarcest resource** (§3.8). |

### 4.1 The ROM-space problem, measured

> **[VERIFIED LOCALLY]** From the byte-exact `vinheim3` link map:
>
> | Region | Free |
> | --- | --- |
> | ROM0 (`$0000–$3FFF`) | `$0033` = **51 bytes**, of which 48 B is the Nintendo logo area (`$0104–$0133`, written by `rgbfix`) and 3 B is the header checksum. **Effectively 0 usable.** |
> | ROMX bank 1 (`$4000–$7FFF`) | `$0058` = **88 bytes** across three gaps |
>
> A separate scan of the ROM image for filler runs ≥ 32 bytes found `$005B–$00FF` (165 B of `$FF`,
> the unused space between the serial interrupt vector and the `$0100` entry point),
> `$62D4–$632F` (92 B), `$64B0–$64CF` (32 B) and `$7FC0–$7FEF` (48 B) — **337 bytes** of in-section
> padding that could be reclaimed.

**Total realistically reclaimable space inside the original 32 KB: ~400 bytes.**

That is enough for a handful of hook stubs and a bank-switch trampoline, and **nothing else**.
kaspermeerts reached the same conclusion independently: *"the game only barely fits in 32 kB, with
only a few dozen bytes to spare."*

**Therefore the ROM must be expanded, and an MBC must be added.** This is not a preference; it is
arithmetic.

### 4.1a Game Boy Color auto-palette: a testing gotcha, not a regression

**[VERIFIED LOCALLY, 2026-08-20]**

Original Game Boy Tetris is a DMG game: four shades of grey, no colour. The familiar blue/red
Tetris palette people see comes from the **Game Boy Color boot ROM**, which colourises
Nintendo-published DMG games automatically.

**The first thing you notice on running the expanded Lab build in mGBA is that it turns
greyscale.** That is an emulator artefact, not a ROM problem:

* The CGB boot ROM's palette lookup uses only the **16 title bytes** (`$0134-$0143`), the byte at
  `$0137` to break ties, and the **old licensee code** at `$014B` (must be `$01` = Nintendo).
  All are **byte-identical** between our stock and Lab builds — title checksum `$DB`, 4th
  character `R`, licensee `$01`. Nothing the MBC1 conversion touches (`$0147`-`$0149`, `$014D`,
  `$014F`) is an input to that algorithm.
* **mGBA does not use that algorithm.** It ships a No-Intro game database at
  `share/mgba/nointro.dat` and matches ROMs by **CRC32**. Our stock build matches
  `Tetris (World) (Rev 1).gb  crc 46df91ad` exactly; the Lab build's CRC `5C61448D` is not in the
  database, so mGBA falls back to greyscale.

**Fix for testing:** in mGBA, *Settings → Game Boy → Game Boy model → **Game Boy Color***. That
forces CGB mode regardless of database recognition.

**A useful side-effect:** mGBA's bundled No-Intro database lists
`Tetris (World) (Rev 1).gb` with `crc 46df91ad` and
`sha1 74591cc9501af93873f9a5d3eb12da12c0723bbc` — **exactly what `build.py --original` produces**.
That is independent third-party confirmation that our build is the genuine verified dump, from a
source we did not choose and cannot influence.

**Still to verify:** that real Game Boy Color hardware colourises the expanded ROM identically.
The analysis above says it must, but it rests on our reading of the boot ROM's inputs. Added to
the Milestone 5 hardware checklist. Any emulator that keys colour off a ROM database rather than
the boot ROM algorithm will show grey — expect users to report this, and document it.

### 4.2 Compatibility of an expanded ROM

* **Emulators:** MBC1 is the most widely and correctly implemented mapper in existence. SameBoy,
  BGB, Emulicious, mGBA, and every reasonable emulator handle it. No risk.
* **Flash carts:** EverDrive GB X3/X5/X7 and EZ-Flash Junior all support MBC1 and MBC5 with SRAM
  saving (EZ-Flash Junior documents MBC1/2/3/5 up to 8 MB; EverDrive GB saves to SD).
* **Original hardware:** an MBC1 ROM runs on a genuine DMG/GBP/GBC **via a flash cart**.
  **It is important not to overstate this as a cost.** A retail Tetris cartridge is **mask ROM** —
  programmed during chip fabrication and physically unwritable — so a modified *image* cannot be
  written to one.
  **CORRECTION (2026-08-20, from `docs/community-research.md` §3.5.7):** an earlier draft said no
  modified ROM can *run* on a retail cart. That is wrong. A **Game Boy Game Genie patches cartridge
  reads at runtime**, so a small hack can run on a genuine unmodified cartridge — limited to
  **three codes**. GB Tetris hackers actively design within that budget (*"I'm trying to keep
  everything within 3 GG codes so it works on hardware"* — mathmaster13). A Lab cannot fit in three
  codes, so this is not a route for us, but **we must not claim it is impossible**: the community
  places real weight on original hardware, and the trade-off will be debated. A flash cart is the price of Game Boy ROM hacking in general,
  not of our expansion decision. What D5 actually costs is narrower: a DIY repro cartridge now needs
  a board carrying an MBC1 and battery SRAM instead of a bare 32 KB flash chip. Emulator, flash
  cart, Analogue Pocket and MiSTer users pay nothing.
  **Note that our situation is genuinely tighter than TetrisGYM's, not merely analogous to it.**
  Retail NES Tetris is already an **MMC1** board (NES-SEROM, iNES mapper 1) with 32 KB PRG, and
  TetrisGYM's default build stays on MMC1 and fits its whole trainer suite into that same 32 KB —
  its `build.js` reports free PRG bytes out of `$8000`. Its MMC3/MMC5/CNROM options buy extra
  capability (a scanline counter, CHR banking), not survival. Game Boy Tetris gives us **~400 free
  bytes in 32 KB**, so expansion is not an option for us — it is the entry price. TetrisGYM does
  demonstrate that changing mapper is *acceptable* to a classic-Tetris community; it does not
  demonstrate that it is *necessary*, and we should not claim otherwise.
* **Recommendation:** MBC1 with 128 KB ROM (8 banks) and 8 KB battery-backed SRAM
  (cart type `$03`, `CART_ROM_MBC1_RAM_BAT`). MBC5 is a fine alternative if we ever exceed MBC1's
  awkward bank-`$20` aliasing, but 8 banks is far from that limit.
* **Nice-to-have:** also produce a **32 KB "purist" build** with no MBC, containing only the
  features that fit in ~400 bytes (realistically: a couple of one-byte-constant trainers). This
  would run on a real Tetris cart reflashed, and is a good marketing/authenticity story — but it
  should be a stretch goal, not a constraint on the main design.

## 5. Phase 5 — ROM hack vs. new implementation

### 5.1 Option A — modify `vinheim3/tetris-gb-disasm`

| Criterion | Assessment |
| --- | --- |
| Authenticity | **Perfect by construction.** Gameplay is the original machine code, bit for bit. Every timing, every quirk, the biased randomizer, the 16-of-18-rows behaviour — all preserved without effort, because they are not reimplemented. |
| Development effort | Low for state-manipulation features (most of them). Higher for new UI. |
| Technical difficulty | Moderate. SM83 assembly, careful VBlank discipline, bank switching. |
| Preserving original gameplay | **Trivially verifiable**: rebuild with all Lab features compiled out and `sha1sum` against the reference. A regression is a hash mismatch. |
| Adding Lab functionality | Good. Free WRAM, free jump-table slots, an existing deterministic piece path, an existing soft reset, existing demo recording. |
| Debugging | Excellent. BGB/Emulicious/SameBoy have full symbolic debuggers and consume `rgblink`'s `.sym` output directly. |
| Maintainability | Assembly is verbose, but the base is heavily commented and organised per subsystem. |
| Extensibility | Good once the bank/hook architecture is in place. |
| Emulator compatibility | Excellent. |
| Hardware compatibility | Good — via flash cart. |
| Uniqueness | **High. No Game Boy equivalent of TetrisGYM appears to exist.** |
| Contributor accessibility | The real cost. SM83 asm is a barrier. Mitigated by a zero-install build and good docs. |

### 5.2 Option B — new engine in GBDK-2020 / C

| Criterion | Assessment |
| --- | --- |
| Authenticity | **The fatal flaw.** To be useful for training, a GB Tetris trainer must be frame-accurate: 23-frame DAS with 9-frame repeat, 2-frame ARE, 93-frame line-clear delay, the exact per-level gravity table, the OR-rejection randomizer with its 10.7 %/13.7 %/16.1 % bias, 1/3G soft drop, left-handed NRS, and the exact scoring. Reproducing all of that in C and *proving* it matches is strictly more work than not changing it — and any residual mismatch invalidates the training. |
| Development effort | Much higher overall, despite feeling easier at the start. |
| Preserving original gameplay | Only by continuous, expensive verification against the original. |
| Debugging / contributor accessibility | Better — C is more approachable. This is Option B's only genuine advantage. |
| Uniqueness | **Low.** "Another Game Boy Tetris clone" is a crowded space. |
| Legal position | Slightly cleaner (no original code), but see §7 — the disassembly route is well-established practice. |

### 5.3 Recommendation

> **Modify the disassembly. Option A. Strongly.**

The decisive argument is not effort — it is that **authenticity is the product**. A training tool
whose physics differ from the game you are training for is worse than useless; it trains the wrong
muscle memory. Option A gets perfect fidelity for free and lets us *prove* it with a checksum.
Option B would spend most of its effort re-earning fidelity that Option A starts with, and would
still never be able to prove it.

Secondary arguments: TetrisGYM itself is the existence proof that this path works; the Game Boy
disassembly scene is mature (four independent byte-exact reproductions verified here); the original
game happens to already contain a deterministic piece source, a soft reset, and dormant input
recording; and the resulting project is genuinely novel rather than the Nth Tetris clone.

**The one real cost** — assembly is a contributor barrier — is manageable and is addressed
directly in `docs/architecture.md` (§ build system) and `CLAUDE.md`.

## 6. Build and toolchain findings

* Verified working: **RGBDS v0.6.1** for `vinheim3`, `kaspermeerts`, `davFaithid`, `dctucker`;
  v0.5.2 also fine for the v1.0 repos. **v1.0.x requires migration work.**
* `make` is *not* required — every repo's build is a handful of `rgbasm`/`rgblink`/`rgbfix`/
  `rgbgfx` invocations that a shell script or `build.py` can drive. This matters: it means the
  project can offer a **dependency-light build** (Python + a vendored RGBDS tarball) rather than
  requiring `make`, `gcc`, and a package manager.
* `rgbgfx` output size depends on the PNG's padded dimensions; disassemblies compensate by
  `truncate`-ing to an exact tile count. Any repo missing those rules will fail to link with a
  "section overlaps" error. Guard this with an explicit expected-size assertion.
* `rgblink -m` (map) and `-n` (sym) output is the basis for both **free-space accounting** and
  **symbolic emulator debugging**. Both should be produced on every build and the map should be
  parsed by CI to report remaining free space, exactly as TetrisGYM's `build.js` does.

## 7. Legal / distribution considerations (Phase 12)

**This is not legal advice.** It is a summary of practical risk and established community practice.

* **The ROM is copyrighted.** Nintendo/TTC/Elorg. Distributing `tetris.gb`, or any build output
  that contains the original game's data, carries real takedown risk.
* **A disassembly is a derived representation of that copyrighted data.** The `pret` community
  (Pokémon, and many others) and the Game Boy disassembly scene operate on the norm that
  *source that reproduces a ROM* is distributed, while *the ROM itself* is not. `vinheim3`'s repo
  follows this norm and is MIT-licensed by its author, but note that **an author's MIT licence
  cannot grant rights over Nintendo's underlying content** — it grants rights over their
  annotation and organisation work. This nuance should be stated plainly in our README.
* **The safest posture, and the one TetrisGYM uses, is patch-only distribution:** publish source
  and a **BPS/IPS patch**; the user supplies their own ROM. TetrisGYM ships only a `.bps` on its
  releases page and refuses to build a patch unless the user provides `clean.nes`.
* **Complication specific to us:** our recommended foundation is a *self-contained* disassembly
  (no `baserom.gb` needed), which means the repository already contains the game in source form.
  We inherit that from upstream either way. Two mitigations, both worth doing:
  1. **Never publish a built `.gb`.** Releases carry a **BPS patch against the v1.1 ROM** only.
     `.gb` is already in `.gitignore`.
  2. **Verify, don't ship.** CI can assert the byte-exact hash without publishing the artifact.
* **Do not distribute** rebuilt original ROMs, modified ROMs, or ROM data in any release, issue,
  or artifact.
* Recommended repository licensing: **MIT for our own Lab code** (compatible with the upstream
  MIT-licensed disassembly), with a prominent `README` notice about the upstream content's status
  and an explicit "you must supply your own ROM" instruction.
